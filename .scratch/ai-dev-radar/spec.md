# ai-dev-radar 看板服务规格

> 由 grilling 共识（2026-09-07/08）+ 原型结论（`prototype/ui-layout` 分支）收敛而成。
> 领域词汇以根目录 `CONTEXT.md` 为准；关键决策见 `docs/adr/`。

## 1. 背景与目标

统计并可视化展示多个研发团队的 AI 研发提效情况。

- **受众**：管理层（横向对比各团队）+ 团队负责人（下钻看本团队趋势）
- **最小数据单位**：团队。不做个人粒度（采集与展示均不做）
- **规模**：团队数不设上限，当前约 4 个

## 2. 指标体系

### 2.1 活动与指标（指标目录初始数据）

**关键研发活动**（8，有版本/迭代维度）：

| 活动 | 指标 |
|---|---|
| SA设计 | IR需求渗透率、SA设计效率 |
| SE设计 | IR需求渗透率、SE设计效率 |
| 开发设计 | AR需求渗透率、开发设计效率 |
| 编码开发 | AR需求渗透率、编码效率 |
| 测试用例生成 | SR需求渗透率、测试用例生成率 |
| 测试用例执行 | 用例执行数、用例执行率 |
| DTS缺陷分析 | DTS分析数、DTS渗透率 |
| DTS缺陷修复 | DTS修复数、DTS渗透率 |

**通用研发能力**（7，仅时间维度）：

| 活动 | 指标 |
|---|---|
| MR代码检视 | AI检视意见数、AI检视率 |
| MR-E2E能力 | AI-MR数量、AI-MR构建率 |
| CodeCheck问题修复 | AI修复数量、AI修复率 |
| 三方件治理 | 治理数量、治理率 |
| 漏洞修复 | AI修复数量、AI修复率 |
| 自动化构建部署 | 能力是否具备（布尔） |
| 白盒安全问题修复 | AI修复数量、AI修复率 |

### 2.2 指标类型与计算口径

指标五种类型：**渗透率 / 效率提升 / 数量 / 布尔 / 比率**。

- 渗透率 = AI 使用数 / 总数（分子分母见事实记录）
- 效率提升 = (Σ预估人天 − Σ实际人天) / Σ实际人天。人天是统一标准，不加权；实际 = 0 时分母按 0.5 人天计；负值如实展示
- **所有率由看板侧基于事实记录的分子分母现算，不存储平台现成比率**（ADR-0001）

### 2.3 指标目录配置化

- 目录存数据库，配置页可增删改查；新增指标 = 加配置，不改代码
- 每个指标声明：所属活动、名称、类型、分子/分母语义、采集方式（`仅补录` / `自动`）
- 第一版所有指标标记 `仅补录`（ADR-0002）

## 3. 维度模型

三个正交维度，任意组合切片：

- **团队**：名称 + 数据源映射（产品版本号、代码仓地址等）
- **时间**：周（周一至周日，Asia/Shanghai）/ 月，由事实记录的时间字段（需求开始/完成时间）聚合
- **版本/迭代**：仅关键研发活动有此维度；团队 × 版本多对多；迭代（如 SCC 27.2.RC1-迭代一）隶属于版本，可跨周/月；按迭代标签聚合出迭代视图

## 4. 数据模型

核心实体：

- **Team**：id、名称、数据源映射（JSON：产品版本号列表、代码仓地址列表等）
- **MetricCatalog**：活动（分两类）、指标条目（如 2.2 声明）、采集方式标记
- **ProductVersion / Iteration**：版本标识、迭代标识（含所属版本）
- **FactRecord**：团队 × 指标 × 迭代（关键研发活动）或纯时间（通用研发能力）× 分子 × 分母 × 时间字段 × 来源标记（auto/manual）× 录入人 × 录入时间。补录粒度：团队 × 迭代 × 指标一条
- **User**：账号、角色（admin / maintainer / viewer）、maintainer 关联团队

## 5. 数据采集

- **采集器接口预留，不实现**：统一接口"输入 = 数据源映射 + 时间窗口，输出 = 事实记录"，获取方式 CLI / MCP / API 三选一（ADR-0002）
- 每日批量采集（APScheduler 内嵌），当前全部指标走手动补录
- **补录**兼作补充（采集不到）与修正（对采集结果有异议）：录入界面按团队 + 迭代选指标填分子分母；自动与手动记录同表，展示时标来源

## 6. 页面规格

五个页面。总览页与团队下钻页的布局/交互以原型为准（`prototype/ui-layout` 分支，结论详见 `.scratch/ai-dev-radar/handoff-prototype-ui-conclusions.md`）：

### 6.1 总览页（原型选定：趋势大图矩阵）
- 每个活动一张大图卡片（两区各一网格）：4 条团队趋势线 + 全公司均值线（灰）；点击某条线下钻该团队
- 颜色跟随团队，固定槽位分配（dataviz categorical 1–4），筛选不重排颜色
- 指标切换在卡片头部（pill 按钮）；布尔活动（自动化构建部署）不画图，直接列各团队具备/不具备
- 悬停十字线读出全部团队数值

### 6.2 全局筛选条（单行，置于所有内容上方）
- 统计维度（按时间 | 按版本/迭代）→ 时间粒度（月|周）或版本选择 → 周期选择（含"全部周期"）→ 展示指标（总览页）
- 作用域覆盖全部图表；维度/粒度/版本切换时周期自动重置为最新
- 迭代维度下：关键研发活动区 X 轴变为迭代；通用研发能力区固定按月趋势（近 6 个月）+ badge 标注"无迭代维度"（固定降级 + 标注，不隐藏）

### 6.3 团队下钻页（原型选定：概览卡平铺 + 目录锚点 + 按需展开）
- 顶部 KPI 行：平均渗透率（关键活动）、平均效率提升（关键活动）、AI检视率、自动化构建部署状态；每 tile = 值 + 环比 delta + 迷你趋势
- 左侧 sticky 活动目录（关键/通用两组，锚点滚动）
- 单列活动趋势卡（本团队 accent vs 全公司均值灰），卡头切指标
- 「详细数据」就地展开：迭代分片对比条形（本团队 vs 均值）+ 分子/分母事实记录表（tabular-nums）

### 6.4 指标详情页
- 跨团队同一指标的趋势对比（复用趋势卡组件）

### 6.5 补录页
- 选团队 → 选迭代（关键研发活动）或周期（通用研发能力）→ 列该范围指标，填分子/分母；提交记录录入人与时间

### 6.6 配置页
- 团队管理（名称、数据源映射）、指标目录管理、用户与角色管理

## 7. 认证与权限

简单登录（本地账号 + session，不接 SSO）：

- **admin**：全部权限（配置团队/目录/用户）
- **maintainer**：按关联团队补录
- **viewer**：只读看板

## 8. 技术栈与部署

- 单服务：**FastAPI** + APScheduler + **SQLite**（预留 MySQL 迁移）+ **React + ECharts** 前端
- 单容器部署；图表样式规范沿用 dataviz（折线 2px、条形 ≤24px 圆角数据端、hairline 网格线、十字线 tooltip、文本不穿系列色）
- 率的计算、迭代/时间两种聚合路径在 `compute` 层统一实现（原型 `prototype/src/data/compute.js` 的 `periodsFor` / `inScope` 逻辑为参照，正式版移植到后端 + 前端共用口径）

## 9. 非目标（明确不做）

- 个人粒度数据的采集与展示
- 实时/准实时刷新（每日批量）
- 采集器的具体实现（仅接口）
- SSO / 对外网暴露
- 单一"提效分"合成指标
