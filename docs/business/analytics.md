# 团队效能分析与成熟度

## 目标和边界

比较多个团队的 AI 研发效能、活动成熟度和短板，提供总览、团队下钻及指标详情。覆盖关键研发活动和通用研发能力；成熟度为人工判断，不是指标推导。看板的需求 KPI 按设计活动与开发活动分别统计：设计活动读取设计记录（IR/SR），开发活动读取开发记录（IR/SR/AR），两者只纳入进展为完成/已关闭的记录，月份按设计时间/开发时间归集，不跨活动相加或去重。测试用例生成/执行、DTS 和研发能力页继续使用 FactRecord；成熟度保持独立的人工评估。看板口径见 [ADR-0017](../adr/0017-dashboard-activity-scoped-requirement-kpis.md)。

## 核心场景

Overview 生命周期小卡片暂不展示代码检视、`dta`（DTS缺陷分析）和 `dtf`（DTS缺陷修复）；它们仍保留在目录、成熟度和适用的专项 FactRecord 页面中。`MR代码检视`属于通用研发能力，其成熟度仅在通用能力模式显示，不并入关键活动矩阵。

洞察拆为三个同级入口：`/` 研发总览面向管理者按“分析筛选 → 月度核心成效 → 周期整体成效 → 核心趋势与研发关键环节并排 → 成熟度矩阵与领域画像、团队表现”阅读。月度和周期核心成效均按设计活动、开发活动两组展示，每组四张 KPI：AI需求渗透率、AI研发提效、AI覆盖需求数、AI提效工作量；两组分别使用自己的活动记录，不合并为单个需求级数值。覆盖说明分别给出设计活动记录数与开发活动记录数及其 AI 状态已维护数、AI 辅助数和完整工作量记录数，不合并。总览研发关键环节固定展示 SA设计、SE设计、开发设计、编码开发、测试用例生成、测试用例执行六张活动卡：前四张按需求角色聚合（SA、SE、实现设计、开发），后两张保留 FactRecord；卡片与趋势说明标注来源。`dta`/`dtf` 只从总览生命周期隐藏，仍保留在目录、成熟度和适用的专项 FactRecord 页面；MR代码检视仍是研发能力页中的独立通用能力。总览核心趋势为 2×2：设计渗透率、设计提效、开发渗透率、开发提效，分别展示团队序列与同活动有值团队的等权均值，不合并为同一条需求序列。团队表现矩阵由设计 4 项与开发 4 项组成 8 列，并分列指标值与变化；选中团队预览该团队设计/开发各自的渗透率与提效四张小图。当前没有业务 Target 或外部行业基准，因此不展示目标达成或外部基准结论。总览非 KPI 模块将说明文字放在模块卡片内；核心趋势与关键环节卡片同排对齐，成熟度矩阵与领域画像同属一张卡，团队表现矩阵与选中团队趋势同属一张卡。成熟度矩阵下方区分有效 `0.0` 和 `1.0–5.0` 热力色阶。`/analytics/activities` 保留八项关键活动的垂直目录：SA设计、SE设计、开发设计、编码开发四项使用需求角色聚合，测试用例生成、测试用例执行与 DTS 继续使用 FactRecord；上方所选活动驱动对应角色 KPI/趋势或 FactRecord 指标，不跨活动平均。下方 Team Difference、指标拆解与业务量、AI提效工作量趋势和原始指标摘要属于页面级整体汇总，始终展示设计/开发双活动，不受活动、活动指标或单周期选择影响，只跟随页面月份/统计周期。原始指标摘要固定四行：设计活动AI覆盖数、开发活动AI覆盖数、测试用例生成数、测试用例执行数。`/analytics/capabilities` 使用能力结构目录选择单项通用研发能力，按目录指标类型展示当前状态、演进、团队差异、证据和独立成熟度。

页面内容区的 PageHeader 负责标题和描述。Dashboard/Analytics 使用流式内容画布及响应式 gutter；Operational 保留表格/操作密度，Readable 用于可读宽度受限的表单。主文档负责 Analytics 纵向滚动；活动与能力目录固定在内容左侧并只管理当前选择，不创建嵌套纵向滚动区。活动页“分析筛选”保留时间粒度、指标和事实周期；统计维度固定为时间，粒度、周期和所选指标写入 URL。旧 `dimension=iteration` 和 `version` URL 状态会被忽略并移除，不提供跨团队版本/迭代筛选，时间事实仍覆盖各版本。总览仅将 `month` 和 `cycle` 写入 URL；`month` 锚定需求活动与 FactRecord 时间窗口并选择成熟度自然月，周期选项为近六个月、本半年度、年度累计，所有窗口截至用户选定月份。总览月度和周期 KPI 使用对应活动/角色聚合的域汇总值；总览趋势、团队矩阵和团队预览以有值团队的等权均值作为“全公司均值”。渗透率/效率由所选范围内的活动记录原始量重算，数量显示活动记录数或人天，不跨团队求和后误称团队平均。需求角色明细使用同活动/角色的团队序列及等权均值，测试/DTS 明细继续使用同指标 FactRecord 序列及 `company_average`；成熟度仍按所选自然月独立计算。总览不按版本筛选，旧 `version` URL 参数不得形成不可见过滤。通用研发能力没有版本范围。Team Detail 的版本候选限于当前团队所属产品。能力页原始指标的粒度控制也位于“分析筛选”工具栏中；成熟度写入迁移到数据管理下的 `/data/maturity`。

活动页的上方目录只选择当前八项关键研发活动：SA设计、SE设计、开发设计、编码开发四项使用对应角色聚合的 KPI 与趋势，测试用例生成、执行与 DTS 使用同类型 FactRecord 的 KPI 与趋势；不跨活动计算率/效率平均。需求角色活动的上方趋势按近六个自然月展示，时间粒度、周期和指标控件仍驱动 FactRecord 查询，不改变角色聚合窗口。下方页面级汇总始终使用设计/开发双活动数据，活动选择/活动指标/活动周期不改变这些值或请求；月份与统计周期改变时下方整体汇总同步更新。设计/开发 AI 覆盖拆解分别保留已辅助、已知未辅助、AI 属性未知三类，不合并；原始指标摘要为设计活动AI覆盖数、开发活动AI覆盖数、测试用例生成数、测试用例执行数四行，缺少来源时保留缺失，不补零或借用其他指标。`company_average` 与 `domain_summary` 仍分别表示有效团队均值和合并原始量，不能互换。通用研发能力按目录实际类型显示：数值类指标保留各自单位与事实，布尔能力逐团队显示已具备/不具备/未知状态，不渲染不存在的 0/1 趋势。所选能力只驱动当前能力的状态、已定义指标、趋势、团队差异和证据；成熟度画像是独立的七项通用能力整体评估，不随目录选择变化，也不推导跨能力总分。选定月份没有事实时显示明确空状态，不回退到其他月份；趋势窗口缺失保留断点，不补零。MR代码检视的业务公式于 2026-10-14 获批：`AI有效检视数` 是 `ai_effective=true` 的 AI 检视意见数；`AI检视有效率` 是有效 AI 检视意见数 ÷ AI 检视意见总数，分母为零时缺失。趋势由意见日期按页面所选时间粒度聚合。有效率以 0–1 比率计算并按百分比展示；数量以条数展示。新增 `mrr-effective-count` / `mrr-effective-rate` 指标保持独立，既有 `mrr-count` / `mrr-rate` 语义不变。意见源只保存稳定 source_id、team_id、意见日期和布尔有效性；本地 API 尚未接入真实代码托管平台。

总览核心趋势为 2×2，分别展示设计/开发活动的渗透率与提效团队序列，以及同一活动内按有值团队等权计算的 `全公司均值`；当前月无记录时保留历史曲线，并明确显示所选月缺数。研发关键环节的四张需求角色卡分别读取 SA、SE、实现设计、开发角色聚合；选中角色后两项趋势展示该角色的渗透率与提效，以同活动/角色有值团队等权均值为基准。测试用例生成/执行卡继续按目录 FactRecord 读取 `penetration` 与 `efficiency` 槽位，图表说明显示原指标名，缺少匹配指标或事实时保留缺失。团队表现矩阵按设计 4 项与开发 4 项分组，每组并列指标值与变化，可在本月与统计周期期间切换。本月变化为当前团队值减前月值；统计周期变化沿用 KPI 周期语义：数量/工作量显示当月贡献，比例/提效显示当前累计值减去加入当月前的累计值。缺少比较输入时保留缺失；全公司均值的变化基于矩阵显示的等权团队均值计算。选中团队后预览该团队设计/开发各自的渗透率与效率趋势，并可进入现有 Team Drill-down。成熟度区按关键活动或通用能力切换，分别显示团队矩阵和本期、上期领域平均雷达；未评估仍为空值。成熟度与团队表现使用并列区域呈现。成熟度矩阵下方补充热力色阶：有效 0.0 使用独立中性色块，1.0–5.0 使用与矩阵一致的等级颜色。

完整团队×能力点矩阵默认收起，展开后包含成熟度领域平均行；桌面固定团队列，移动端保留局部横向滚动提示。活动页按时间筛选，时间事实跨版本/迭代纳入；页面不提供跨团队版本/迭代筛选。时间粒度为月/周/日，周期可选全部或单周期，指标可切换为全部或单项；时间窗口分别为近六个月、近十二周、近三十天，成熟度始终按独立的自然月。通用研发能力原始指标可切换月/周/日，成熟度仍固定按自然月；布尔能力使用团队状态列表，不绘制 0/1 折线或全公司均值。Team Drill-down 以“整体表现 → 研发关键环节 → 成熟度画像”组织单页故事线，并提供 sticky 锚点导航。整体表现的月度与周期两行均按设计活动、开发活动两组各四项需求 KPI 展示，主值取当前团队对应活动/角色的汇总；版本筛选同时过滤设计/开发记录（各按自身 `version_id`），未选版本时领域比较取同一活动有值团队的等权均值；选中版本时当前团队值按版本过滤，领域参照取同时间范围、同活动、所有团队且不限版本的有值团队等权均值；界面明确标注两个范围，只展示当前团队与参照差异，不称同版本排名。率/效率周期值按原始量重算，数量/工作量周期值为所选周期累计，变化显示当月贡献，不生成跨 KPI 综合值。月份、统计周期和版本位于页面顶部的全局筛选；核心趋势分别展示当前团队设计/开发活动的渗透率与提效，并以同活动/角色领域均值作基准。研发关键环节的 SA设计、SE设计、开发设计、编码开发使用需求角色聚合，测试与 DTS 继续读 FactRecord；FactRecord 卡固定展示 `penetration` 与 `efficiency` 类型两个槽位，来源指标名保留在说明中，缺失类型不由其他类型替代。当前实现中，团队下钻角色卡的当月值以所选月份为锚点：时间粒度为周/日或周期为全部时回退到所选月份，趋势仍按所选统计周期展示；该回退是已记录的验证边界，不代表最终交互口径。团队效率趋势超出图轴 ±100% 时只钳制绘制点，tooltip 保留原始值与比较信息。成熟度画像分别覆盖关键活动和通用能力；矩阵/雷达比较团队本期、团队上期与领域本期平均，团队记录取所选自然月的前后两个月，未评估分值保持为空，0 分保留为有效值。指标详情按 Result → Comparison → Evidence 展示：当前全公司均值、同指标趋势与单指标团队排名/状态，以及按需展开的当前周期原始事实。量化详情分列 `company_average` 与 `domain_summary` 的结果、原始分子/分母；前者为团队结果算术平均，后者合并原始量后重算，不互相替代。目录类型仍决定率、数量或布尔展示。团队、版本、迭代、时间粒度与时间字段影响对应事实查询；通用研发能力不支持迭代维度。

图表按分析任务而非指标存储类型选择：时间演进优先折线，单周期团队排名使用单指标排序，布尔能力使用状态列表；数量指标不因类型被强制改为柱状趋势。

## 指标规则

- 每个逻辑键优先最新人工事实，否则取最新自动事实；同时间按 ID 决定顺序。关键活动键为团队/指标/迭代，纯时间键为团队/指标/开始与结束日期。
- 日/周/月按选定开始或结束日期归属，日期采用 Asia/Shanghai；迭代按标签归属，不按日期重新分配。日周期是自然日，空档保留为空周期。
- 渗透率/比率为合计分子除以合计分母，分母非正返回空值。数量为合计分子。效率为 `(合计预估 - 合计实际) / 合计实际`；实际非正时使用 0.5 人天，二者均为 0 时返回空值。需求活动 KPI 的渗透率分母为对应活动/角色 AI 使用状态已维护的记录；效率仅对 AI 使用为“是”且预估、实际工作量完整的记录计算；计数单位为活动记录，不跨活动去重。
- `company_average` 保留各非空团队指标值的算术平均；`domain_summary` 合并团队原始数再计算，二者不能混用。
- `/api/compute` 每个团队/周期事实点提供 `fact_count`；无事实的数量点保持缺失，已记录的数量事实 0 保持为 0。`company_average` 只平均该周期有事实且结果有效的团队。
- 研发能力页团队差异中的团队名称可进入对应的 Team Drill-down；导航保留当前 URL 中的分析状态并携带来源，Team Detail 入口在侧栏与面包屑中保持明确，返回按钮回到来源页面。直接打开 Team Drill-down 时默认返回总览；新页面从顶部开始。
- Activity 页工作量趋势按设计活动、开发活动分别展示：柱表示当月 AI 辅助记录的预估减实际人天合计，蓝色为柱色；同比线逐月比较去年同月：`(本月工作量 / 去年同月工作量) - 1`，去年值缺失或非正时保留空点，不以零或其他周期替代。两条活动序列独立展示、不合并，也不创建 FactRecord 效率综合指标。
- 研发能力页状态区只显示所选能力目录中已定义的指标。FactRecord 数量使用 `domain_summary` 合并总量，比例/效率/渗透率使用同指标 `company_average`；变化与迷你趋势跟随卡片使用的同一序列，证据表继续分列团队均值、合并结果、原始量、事实覆盖和同指标趋势。团队差异使用各指标独立的相对热力色阶，缺失值无色；色阶只表达同列数值大小，不表示质量或绩效好坏。MR代码检视有效意见指标读取本地 AIReviewOpinion 源记录；数量按有效意见数合并，率按各团队比例等权展示，零分母缺失。意见日期按页面时间粒度分组；真实平台采集仍未实现。
- 研发能力成熟度画像使用现有七项通用研发能力作为矩阵维度，按团队展示所选月评分，并用当前/上期领域平均作雷达对比。该整体画像不随能力目录选择变化；每队/能力/月只有一项分值，不推导子维度、不跨能力求总分或补零。能力页统计范围是所选粒度的最新单期快照及近六个月/十二周/三十天趋势；版本筛选不适用，因为通用能力没有迭代归属。
- FactRecord 活动趋势使用同指标 `company_average`；需求活动 KPI 卡使用对应活动/角色聚合的 `domain_summary` 汇总值，趋势和团队表使用该活动有值团队的等权均值。缺少 AI 使用状态或所需工作量字段时保留空值。
- 未设置单周期的布尔能力当前状态使用最近有效 `snapshot`；明确选择单周期的布尔详情读取该周期 `series.values`。缺失保持未知、不当作 false，也不回退到其他周期；布尔指标不生成全公司均值趋势。数量柱图仅用于指标详情。

总览测试用例生成/执行两张 FactRecord 趋势使用该活动同指标、各有事实团队值的等权算术平均作为基准，界面名为“领域平均”。该值对应 `/api/compute` 的 `company_average`；`domain_summary` 是合并原始分子/分母后重算的结果，不用于这两张领域趋势图。需求角色卡的渗透率/提效基准是同一活动/角色下有值团队的等权均值，也不使用 `domain_summary` 替代。缺少团队事实的周期仍为空，不补零。

## 需求活动 KPI 口径

看板需求 KPI 分设计活动与开发活动两组，分别对四条全局 KPI 计算；两组使用各自的记录，不跨活动相加，也不按需求编号跨活动去重。计数单位是活动记录，不声称“唯一需求数”。

- 范围：设计活动读取 `ir_requirements`（IR/SR），开发活动读取 `development_requirements`（IR/SR/AR）；只纳入进展为完成或已关闭的记录，月份按设计时间/开发时间（内部 `completed_at`）归集。
- AI需求渗透率：AI 辅助为真的活动记录数 ÷ 对应活动/角色 AI 使用状态已维护的记录数；未知状态不进入分母，`AI适用性` 不参与该口径。
- AI研发提效：AI 辅助且预估、实际工作量完整的记录，分别合计后按 `(预估合计 − 实际合计) ÷ 实际合计` 计算；实际值非正时沿用 0.5 人天分母回退，预估和实际均为 0 时结果缺失。
- AI覆盖需求数：AI 使用状态为真的活动记录数；存在已知状态但没有 AI 辅助记录时结果为 0，全无已知状态时结果缺失。
- AI提效工作量：仅对 AI 辅助且预估、实际工作量完整的记录汇总 `预估 − 实际`，单位为人天；已知无 AI 辅助记录时结果为 0，状态未知或工作量缺失时不补零。

活动级 AI 使用状态：设计活动为 SA 或 SE 任一为“是”，开发活动为实现设计或开发任一为“是”。角色级 KPI 只使用该角色自己的 AI 标志与工作量字段：SA、SE、实现设计、开发互不合并。覆盖说明分别给出设计活动记录数、开发活动记录数，以及各自的 AI 状态已维护数、AI 辅助数和完整工作量记录数，不合并为一个总数。

月度和周期卡片采用对应活动/角色的原始记录合计口径；趋势和团队矩阵中的“全公司均值”按有值团队等权。设计活动总工作量优先使用旧总量字段，缺失时由 SA+SE 分项求和；开发活动工作量为实现设计+开发求和。两个活动的 KPI 独立展示，不推导 SR、AR 或跨活动合计结果。无记录时显示“暂无记录”，不以 0% 或 0 人天代替。

Team Drill-down 未选版本时，需求活动 KPI 与趋势基准使用同一活动有值团队的等权均值，界面标为“有数据团队等权均值”；选中具体版本时，当前团队值按版本过滤（设计/开发记录分别使用自身 `version_id`），领域参照仍按相同时间范围、相同活动、所有团队且不限版本计算，并分别标明两类数据范围。时间趋势直接对照同粒度的版本化团队结果和无版本领域均值。FactRecord 环节的迭代趋势仍以所选迭代起止日期切取无版本日事实，按既有指标公式先在团队内汇总，再对有有效结果的团队等权平均；未选具体版本时仅在有事实团队中等权，标为“有事实团队等权均值”。参照不使用其他团队的版本排名。只有一支团队有需求活动值时，提示多团队对照不可用；缺失团队仍为空值。版本筛选不得改变用户选定时间范围；无匹配事实保持缺失。

## 成熟度规则与生命周期

记录唯一粒度是团队/活动/评估月。分值 0–5，最多两位小数；保存规范化十进制字符串，使用 Decimal 计算。团队等级为 floor；领域按已评估团队等权平均后 floor，展示四舍五入不影响等级。未评估不等于 0，部分评估需要保留覆盖信息。

新月份不自动继承。维护者可显式预览并复制上月，确认后保存；清空删除对应月记录，恢复未评估。admin 可维护全部团队，maintainer 仅绑定团队，viewer 只读；后端再次校验权限。

## 数据与实现映射

目录 Activity/Metric、FactRecord、Team、ProductVersion/Iteration 支持事实查询；目录由代码/种子维护，指标字典只读展示，不从 UI 配置；MaturityRecord 独立支持评估。

本地演示种子按执行时的 Asia/Shanghai 当前月生成近六个月事实与独立的成熟度模拟评估，覆盖四个团队及目录中全部活动和指标；当前月的事实落在执行当天。演示评估只用于界面预览，不由事实指标推导，也不改变正式评估的人工维护规则。跨入新月份后须重跑种子才覆盖新的默认月份；该命令会重建业务数据。

### Activity selection and monthly raw-summary behavior

The Activity page commits a new directory selection only after the new Activity's metric requests settle. During the request, its previous upper workspace remains visible with a pending announcement; title, selected item, KPI rows and trends switch together. Failure uses the selected Activity's own error state. The four requirement role activities (SA设计, SE设计, 开发设计, 编码开发) use role aggregates; tests and DTS keep FactRecord. Page-wide lower summaries are independent of Activity selection: Team Difference, design/development coverage breakdown and design/development workload trends follow the selected statistics cycle, while the four-row raw metric summary follows only the selected month. The raw summary rows are 设计活动AI覆盖数, 开发活动AI覆盖数, 测试用例生成数 and 测试用例执行数; columns remain `本月数值`、`上月数值`、`环比变化`、`趋势`. Count delta is current minus previous only when both points have facts; the trend uses the same source over six months and leaves missing periods blank.

Activity raw-summary presentation: keep metric provenance on each row's accessible name and title; the visible data columns remain exactly `本月数值`、`上月数值`、`环比变化`、`趋势` in addition to the metric-name column. The four rows retain equal geometry for full, partial, empty, loading and error states.
