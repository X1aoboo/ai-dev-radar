# Data Management Module

## 职责与接口

`data_api.py` 负责组织层级、设计活动与开发活动需求记录、临时导入/采集批次、审计查询和本地 AI MR 检视意见的 HTTP 编排；`api.py` 的 `GET /api/catalog` 提供只读指标目录；`data_management.py` 提供活动需求记录的规范化、CSV/XLSX 标准库解析、差异、空字段/覆盖更新、有效记录筛选和计算，并接受活动 profile；`requirement_fields.py` 定义通用字段 spec、`DESIGN_PROFILE` 与 `DEVELOPMENT_PROFILE`，`ir_fields.py` 保留设计兼容导出；`requirement_template.py` 用标准库生成 21 列设计模板和 19 列开发模板，`ir_template.py` 保留设计入口；`requirement_imports.py` 承接两个活动文件导入与设计采集共用的逐行校验、名称引用解析、查重、批次创建和更新模式，`ir_imports.py` 是设计兼容 wrapper；`team_excel.py` 用标准库生成团队人员模板/导出工作簿，`team_imports.py` 负责团队人员行校验、团队自动创建、工号 upsert 和整批事务。`AIReviewOpinion` 保存最小意见来源字段，`/api/data/code-review/opinions` 提供带团队权限和日期/分页过滤的读取，稳定 `source_id` 的 PUT 执行幂等新增/更新；派生指标由 `/api/compute` 调用 `code_review_metrics.py` 聚为团队/日事实，并复用现有序列计算器。该本地 API 不表示 Gateway 已实现代码检视采集。`gateway_api.py` 是 admin-only Gateway 配置、检测、激活、放弃及审计 API；`gateway_config.py` 管理唯一 Active/Draft、revision、Token 复用和不可变 runtime snapshot；`gateway_health.py` 校验 Readiness 响应、保存最新状态并提供 stale/状态转换；`gateway_contracts.py` 是 Readiness 消费端模型。`source_collection.py` 管理窗口、团队隔离和运行记录；`collector_gateway.py` 只负责接收 runtime snapshot 并发同步 Bearer HTTPS 请求，`collector_contracts.py` 是 IR v1 的消费端模型。`schemas.py` 定义 Radar API DTO，`models.py` 定义存储；本模块复用 `auth.py` 与 `db.py`。

前端按需求、问题单、MR、代码检视组织数据源入口。`DataManagementPage` 在需求工作台组合「设计活动 / 开发活动」两个页签，分别连接设计接口与开发接口；问题单、MR、代码检视使用明确的待定义页面。活动页路由为 `/data/requirements/design`（默认）与 `/data/requirements/development`，旧需求类型路径由路由层兼容重定向，不改变后端接口。

`DataManagementPage` 与 `App.jsx` 拥有业务路由和交互；共用 `PageHeader`、`FilterToolbar` 及 `frontend/src/design/design-system.css` 中的 `.operational-table`、状态、紧凑反馈和系统管理 workspace 样式。`/settings/products` 使用全宽 `management` 产品层级页（`ProductHierarchyPage`），按团队 → 产品 → PI（产品版本）→ 迭代展开，PI 下迭代可选；`/settings/teams` 使用全宽 `management` 团队人员目录（`TeamPersonnelPage`），左侧团队目录、右侧全部成员表格、行内编辑和新增/编辑弹窗，团队角色固定为 SA/SE/MDE/开发/测试；`/settings/gateway`、`/settings/collections`、`/settings/users` 使用全宽 `admin` 页面：Gateway 为状态摘要/Active-Draft/检查清单/审计与配置弹窗，Collection 为 Gateway 就绪条/采集范围/定时与手动并排/全宽运行历史，Users 为账号摘要/全宽表格/角色说明/轻量团队绑定与弹窗；`/settings/metrics` 的指标字典使用只读全宽 `catalog` 页面，按活动分组展示业务口径、公式、数据来源、使用位置和缺失处理，不提供活动/指标写入口或源数据规则试算；`dataManagement.css` 保留成熟度、表单和其他页面级工作台布局。活动需求工作台由 `frontend/src/dataManagement/requirements/` 的 `requirementProfiles.js` 驱动通用 `RequirementWorkbench`、`RequirementDataGrid`、`RequirementFilterBar`、`RequirementRecordDrawer`、`RequirementImportWizard` 和 `RequirementSummaryStrip`，并保留现有 `ir-workbench.css` 与 `.ir-*` 视觉层；`/data/*` 使用全宽 `workbench` 内容模式，表格内部滚动、分页贴底，支持列分组、视图预设、列设置、密度、排序、内联编辑和批量保存。维护者需求/成熟度范围从账号绑定团队取值，前端禁用选择并说明原因，后端仍负责授权。设计活动的待确认采集批次只在有内容时显示，可打开共享复核抽屉；开发活动没有采集区域。`App.jsx` 的问题单、MR、代码检视使用共享 StatusPage 呈现紧凑待定义状态，不建立新数据契约。

`App.jsx` 按路由分配 `dashboard`、`analytics`、`workbench`、`catalog`、`management`、`operational` 和 `readable` 内容模式；`/data/*` 使用 `workbench`，`/settings/teams` 与 `/settings/products` 使用全宽 `management`，`/settings/gateway`、`/settings/collections`、`/settings/users` 使用全宽 `admin`，`/settings/metrics` 使用全宽 `catalog`，其他 `/settings/*` 使用 `operational`/`readable`。活动需求工作台与成熟度在引用数据加载时保持页头/范围筛选结构，Loading 只占工作区；路由级 lazy loading 由 AppShell 的 Suspense 保留共享壳。`App.jsx` 的问题单、MR、代码检视只渲染紧凑待定义状态，不建立新数据契约。

主要接口为设计活动 `/api/data/ir`、`/api/data/ir/schema`、`/api/data/ir/import-template`、`/api/data/ir/bulk`、`/api/data/ir/{record_id}`、`/api/data/ir/imports/preview`、`/api/data/ir/imports`、`/api/data/ir/imports/{batch_id}`、`/api/data/ir/imports/{batch_id}/confirm`、`/api/data/ir/{record_id}/audit-logs`，以及同形的开发活动镜像 `/api/data/development`、`/api/data/development/schema`、`/api/data/development/import-template`、`/api/data/development/bulk`、`/api/data/development/{record_id}`、`/api/data/development/imports/preview`、`/api/data/development/imports`、`/api/data/development/imports/{batch_id}`、`/api/data/development/imports/{batch_id}/confirm`、`/api/data/development/{record_id}/audit-logs`；组织接口继续使用 `/api/teams/options`、`/api/collection-schedules`、`/api/collection-schedules/{domain}`、`/api/collection-schedules/{domain}/run`、`/api/gateway`、`/api/gateway/draft`、`/api/gateway/draft/check`、`/api/gateway/draft/activate`、`/api/gateway/active/check`、`/api/gateway/audits`、`/api/gateway/status`、`/api/catalog`、`/api/data-metrics/overview`、`/api/teams/import-template`、`/api/teams/export`、`/api/teams/imports/preview` 及 `/api/teams/imports/confirm`。活动/指标写接口和源数据指标规则接口已移除。`GET /api/data/ir` 与 `GET /api/data/development` 支持字段筛选、`requirement_type` 类型筛选、关键词、排序和筛选范围 `summary`；`PATCH /api/data/ir/bulk` 与 `PATCH /api/data/development/bulk` 批量保存内联编辑，整批事务、逐行权限校验和审计；`PATCH /api/data/{ir|development}/{record_id}` 单条更新；`POST /api/data/{ir|development}/imports/preview?mode=upsert|fill_empty` 保存批次更新模式；`GET /api/data/{ir|development}/import-template` 分别生成 21 列设计模板和 19 列开发模板。开发活动文件导入只允许 `source_kind=import`，批次与审计 domain 为 `development`；设计活动采集批次继续使用 `source_kind=collector` 和 legacy 校验。`/api/gateway/status` 只读返回 configured/status/stale/last_known/checked_at/latency/contract/error 投影，不返回地址、Token、Draft 或审计；`/api/teams/options` 只读返回 id/name 供身份绑定；`/api/catalog` 只读返回活动及其指标，供指标字典和看板目录使用；`/api/data-metrics/overview` 是研发总览专用的只读聚合接口，限制 1–12 个月窗口并接受可选 `version_id`，只读取设计记录中 `requirement_type=IR` 的类型；复用需求查询权限，maintainer 只看到绑定团队。响应只含团队/月度 AI 属性计数、完整工作量合计和域汇总，不含需求标识或人员字段；它不改变 `/api/compute` 的 FactRecord 契约，也不写入指标结果。采集计划接口额外返回只读 `CollectionScopeOut(team_count/pi_count/derived_from)`，采集页用它展示范围；聚合函数位于 `data_management.py`，HTTP 查询和授权仍由 `data_api.py` 编排。Gateway 管理接口均为 admin-only；读取 DTO 只给 `token_configured`，不返回 Token。方法和参数以路由、DTO 与运行时 OpenAPI 为准。跨服务能力语义及 Gateway 线协议见 [AI 研发数据网关能力协议](../../contracts/ai-dev-data-gateway/README.md)。

## 临时态与事务

ImportBatch 保存 domain（`ir` 或 `development`）、source_kind、可空 team_id、filename、`update_mode`、created_by、pending/confirmed；ImportRow 保存规范化 payload、Gateway source_system、差异、错误、警告、目标及 valid/invalid/applied 状态。旧文件批次的 team_id 保持 NULL。预览持久化临时数据，计算函数不读取它们。`update_mode` 为空时按 `fill_empty` 处理。CollectionSchedule 按域保存启用状态、hourly/daily/weekly/monthly 节奏及 Asia/Shanghai 时间字段；CollectionRun 保存窗口、触发者、Active 配置 ID/base URL、运行级错误、整体状态和团队级结果，不保存 Token；IR 初始禁用。`gateway_configurations` 的 slot 唯一约束保证全局最多一条 active 与一条 draft，`gateway_health_status` 每个 scope 仅保留最新观察，`gateway_config_audits` 不存凭据。新增表由 `Base.metadata.create_all` 建立；`ensure_ir_schema()` 为既有 `ir_requirements` 增加模板字段并为 `import_batches` 增加更新模式，`ensure_development_schema()` 建立独立 `development_requirements` 表并使既有库可增量启动，不改动 `ir_requirements` 列或回填历史记录；`ensure_gateway_schema()` 为既有 `collection_runs` 增加可空快照和全局错误字段。

确认先检查批次权限、pending 状态和无效行，再逐行重新校验 DTO、层级引用和团队写权限。管理员可查看/确认所有采集批次；维护者只能查看/确认所属团队的采集批次。普通文件预览的 source_kind 固定为 import；仅内部采集路径创建 source_kind=collector 并必须绑定 team_id。开发活动只接受文件导入，批次与审计 domain 为 `development`。按 requirement_no 在对应活动域查询正式记录：不存在则新增，存在时按批次 `update_mode` 调用 `overwrite_non_empty_fields`（upsert）或 `merge_empty_fields`（fill_empty）。旧 pending 文件批次确认时按当前活动模板重新校验，不符合时要求重新预览；采集批次保留 legacy 校验。更新正式记录、AI 字段元数据、AuditLog、行 applied 及批次 confirmed 在一次事务提交；异常 rollback。采集审计 action 为 `collector_confirm`，文件导入为 `import_confirm`；页面 PATCH/bulk 是显式覆盖，不能复用补空合并语义。`_effective_changes` 只审计实际变化的字段。

## 数据与计算边界

Team 聚合保存名称和成员；`source_mapping` 是 Gateway/采集的持久化集成字段，不进入团队人员页面的读写路径。团队人员导入模板列为团队名称/工号/姓名/角色，团队不存在时创建，工号存在时更新姓名/角色/团队；预览不写业务数据，确认时重新校验并单事务提交，任一行错误整批拒绝。导出包含成员和团队两个工作表，admin/viewer 全部、maintainer 仅绑定团队。团队人员页只提交名称或成员字段；`TeamIn.source_mapping` 在创建时可省略并落为空映射，更新名称不会清除既有映射。产品/版本/迭代由 Product/ProductVersion/Iteration 聚合维护，产品通过 `team_id` 关联团队。团队角色使用 SA/SE/MDE/开发/测试，系统登录角色仍为 admin/maintainer/viewer。IR Gateway 的采集范围从团队下的 ProductVersion/PI 派生，`source_mapping.product_versions` 不再参与该链路，只保留作旧采集链路的持久化兼容字段。

Product/ProductVersion/Iteration 聚合仍为团队 → 产品 → PI → 迭代：产品只有一个 `team_id`；PI 是 `ProductVersion`，对应需求记录的 PI/`version_id`；迭代属于 PI 且可选。产品页面不新增持久模型，只提供全宽层级工作台和紧凑弹窗。

`IRRequirement` 保存设计活动记录：需求标识、需求类型（IR/SR）、产品/版本/迭代、设计时间（兼容字段 `completed_at`）、责任工号、所属功能（可空）、进展、SA/SE 姓名与工号、SA/SE 工作量、AI 质检等级（含「不合格」）/适用性/使用状态/研发模式、备注及旧场景字段。`DevelopmentRequirement` 保存独立开发活动记录：类型（IR/SR/AR）、需求标识、产品/版本/迭代、实现设计责任人与开发责任人、实现设计/开发工作量、AI 适用性/使用状态/研发模式、开发时间、备注。需求编号在各自活动域内唯一，同一编号可同时存在于设计与开发记录；人员匹配不决定归属。设计记录有效性只要求需求编号、标题、产品/版本/迭代和设计时间，历史设计记录不因缺少后来新增的必填字段失效；开发记录为新域，有效性要求类型、需求编号、标题、进展、产品/版本/迭代、实现设计/开发责任人和开发时间。新增必填只约束新建和文件导入，历史记录不追溯判无效。设计总工作量按“旧总量优先、否则 SA+SE 求和”读取，设计 AI 汇总按 SA/SE 使用状态推导并保留旧 `ai_assisted`；开发 AI 汇总按实现设计/开发使用状态推导。指标目录由 `seed.py` 的 CATALOG 维护，页面只读展示；指标公式由指标类型和 FactRecord 分子/分母语义决定，页面不提供通用指标定义或源数据规则配置。

IR Gateway 路径使用严格同步 `POST /v1/collections/ir`。Radar 仍按团队编排，但请求只携带 request_id、从团队版本配置和本地层级展开的 `{product_name, version_name}` 列表及带时区半开窗口，不发送团队名称。Gateway 记录最多 10000 条；响应不能包含 Radar 本地 ID 或契约外字段。Radar 按 product_name 与 version_name 联合校验本地版本及请求范围，再在该版本下按 iteration_name 解析；`business_module` 的 null、空字符串和纯空白在暂存前规范化为 `通用模块`。重复 source_id、范围外产品版本、引用缺失/歧义、额外字段或类型错误进入无效行，整批禁止确认。product_versions 配置为空时跳过；空响应成功且不建批次；团队失败继续处理其他团队，不自动重试。

SourceCollectorRegistry 保留原接口，但 IR v1 由 `source_collection.py` 直接经 AI 研发数据网关执行；旧定时任务仍使用 CollectorRegistry 的 FactRecord 链路。采集调度与 `gateway-health-check` 共用当前单进程 APScheduler，不做分布式锁。健康检查启动时立即运行一次，之后每 30 秒运行；Draft 只在人工请求时检测。状态判定包含 AUTH_FAILED、SERVICE_MISMATCH、PROTOCOL_INCOMPATIBLE、readiness 503 的 DEGRADED、连续网络失败 1–2 次 DEGRADED/第 3 次 UNREACHABLE，以及 90 秒 stale。激活 Draft 重新实时检测并核对 revision；新结果只在仍对应当前配置时写回。新鲜的确定性 Active 错误可以写为单条 CollectionRun 全局错误；未知、过期、DEGRADED 或 UNREACHABLE 不阻断真实 IR 请求。ADR-0003 表达源数据优先方向，不意味着旧 `/api/compute` 已切换到 IR。Gateway URL、Token 和超时由设置页存入 Radar 数据库；Token 按 ADR-0010 明文存储，但永不出现在日志、HTTP 输出、审计或 run 中。真实内部 Gateway 尚未联调验证。

## 失败和验证

引用不一致、无效文件/字段或批次错误返回验证失败；越权拒绝；重复资源和重复确认返回冲突。文件解析支持 CSV/XLSX、UTF-8/GB18030、Excel 日期序列号、首个工作表、空行跳过和重复表头检测；不宣称支持任意 Excel 工作簿特性。模板生成与解析均不引入第三方 Excel 库。
